# PKC 工作台统一数据与跨页面联动设计

日期：2026-10-21

状态：用户已确认设计方向，待审阅本文

## 1. 目标

让赛事工作台的队伍资料、赛程、对局数据和当前场次在各页面之间保持一致，并让操作者能清楚知道下一步去哪里。

成功后：

- 同一份队伍资料只维护一处；导播台、赛程和宣传图使用同一份队伍身份与名单。
- 对局页选择系列赛、赛程场次或小局后，工作台顶栏、导播台和 OBS 都跟随同一上下文。
- 多标签页出现过期上下文时能发现并提示，不再静默覆盖。
- 概览页按赛前、赛中、赛后给出可直接跳转的下一步，同时保留侧栏自由导航。
- 现有 JSON 文件、书签 URL、直播场景和赛事数据在渐进迁移中继续可用。

## 2. 现状与问题

- 对局数据、队伍库和赛程由 `assets/pkc-core.js` 通过 `/api/store/*` 读写 JSON；页面脚本也直接使用这些通用接口。
- `director/routes.mjs` 的 `/api/director/teams` 读写 `数据/teams.json`，并把 `数据/library.json` 当前系列的队伍作为补充。这与工作台设计文档所定的队伍库权威 `library.json` 不一致。
- 当前上下文由生成器写入 `数据/context.json` 和 `/api/director/context`，后者更新进程内导播状态并通过 SSE 广播。浏览器端不等待部分写入，也会忽略发布错误；页面刷新时的自动发布可能让旧标签页覆盖新选择。
- `preview` / `onAir` / `live` 是不同用途的导播运行态。它们应继续保留，但 `live.context` 应是持久化上下文的服务端投影，而不是第二个可独立编辑的数据源。
- `director/console.html` 是当前工作台和导播台页面；`director/director.html` 是旧页面，仍留在仓库中，容易让维护者不确定应修改哪份。
- 当 `/api/ping` 不可用时，`STORE` 会静默转为浏览器 `localStorage`。这会造成“页面看似已保存、服务器数据却没有变化”的双来源体验。

## 3. 架构选择

### 选择 A：在现有 JSON 存储上建立统一领域服务（推荐）

增加小型服务端领域层，负责队伍、赛程、对局与上下文的读写、校验、迁移和发布。保留现有 JSON 文件和接口作为短期适配层，按阶段迁移页面。成本和数据风险最低，也符合当前单机、单操作员的运行方式。

### 选择 B：迁移 SQLite

关系和事务约束更强，但需要数据库迁移、备份恢复策略和新的运行时依赖。当前重复来源可以在 JSON 层解决，迁移的额外风险暂时不值得。

### 选择 C：只调整工作台导航

能让页面更容易找到，但不解决队伍双写、上下文覆盖和存储失败被隐藏的问题。

本设计采用选择 A。暂不引入数据库或前端框架。

## 4. 数据权威与职责边界

| 领域数据 | 唯一权威 | 写入职责 | 只读消费者 |
| --- | --- | --- | --- |
| 系列赛、队伍身份、队徽、选手名单 | `数据/library.json` | 队伍库及系列赛管理 | 对局数据、赛程、导播台、宣传图、OBS |
| 分组、抽签、对阵、比分、晋级 | `数据/bracket.json` | 赛程页面 | 对局数据、概览、导播台、OBS |
| 单局战绩与 `matchKey` | `数据/matches.json` | 对局数据页 | 赛程汇总、概览、导播台、OBS、导出 |
| 当前系列赛 / 场次 / 小局指针 | `数据/context.json` | 对局数据页经上下文服务提交 | 工作台顶栏、概览、导播台、OBS |
| 英雄选择、禁用与头像标签 | `数据/heroStats.json` | 英雄胜率页面与抓取导入 | 英雄胜率、解说胜率查询 |
| 导播预览 / 在播设置 / 现场计时器 | 服务端 `preview` / `onAir` / `live` 状态 | 导播台控制及明确标注的现场操作 | OBS 与工作台状态展示 |

`live.context` 只是 `context.json` 的运行态投影；服务启动时从磁盘初始化，后续只能由上下文服务更新。OBS 页面只消费状态，不写赛事数据。

### 4.1 队伍资料迁移

`teams.json` 进入只读兼容期，不再接受新的独立写入。迁移采用预览报告 + 用户确认：

- 以队伍 ID 精确匹配；无 ID 匹配时，再按规范化队名提示可能重复项。
- 已匹配队伍的冲突字段不自动覆盖 `library.json`；报告差异供用户选择保留值。
- 未匹配队伍必须选择目标系列赛后才导入。
- 写入前生成 `数据/_backup` 备份；原 `teams.json` 保留到用户确认迁移结果并经过一个完整赛事周期。
- 导入操作可重复执行而不重复建队。

迁移工具首先提供只读预览模式，不在服务器启动时自动改数据。

## 5. 服务端分层与接口

```text
工作台页面 / 生成器页面 / 导播台 / OBS
                 │
       页面控制器与 URL 导航
                 │
      HTTP 路由（输入校验、兼容）
                 │
领域服务：队伍 / 赛程 / 对局 / 上下文
                 │
       JSON 仓储与原子备份
```

- `server.mjs` 逐步收敛为静态服务、通用 HTTP 帮助函数和路由注册，不再继续累积领域规则。
- 路由负责 HTTP 解析、状态码和兼容映射；领域服务负责验证、冲突检测、数据联动；JSON 仓储负责原子写入和备份。
- OBS 是只读渲染端；`director/routes.mjs` 保留场景预览 / 推送以及 SSE，但上下文更新委托给领域服务。
- 新的领域接口：`GET/PUT /api/competition/teams?seriesId=<id>` 操作明确指定系列中的队伍清单；`GET/POST /api/competition/context` 读取和提交当前指针。
- 现有 `/api/store/*`、`/api/director/teams`、`/api/director/context` 先保留为适配器，内部调用同一领域服务。页面迁移完成并有引用检查后才讨论移除。

## 6. 上下文一致性协议

上下文对象包含 `seriesId`、`matchKey`、`gameId`、展示用标签、双方队伍 ID/名称，以及服务端维护的 `revision` 和 `updatedAt`。

1. 页面初始化时读取服务端当前上下文与 revision；初始化只读，不把页面缓存的旧值自动发布回服务端。
2. 用户明确切换系列赛、场次或小局后，页面向 `/api/competition/context` 提交上下文和所见 revision。
3. 服务端验证引用存在后，先原子保存 `context.json`，再更新 `live.context`，最后发送 SSE。广播不会先于持久化成功。
4. 每次有效变更递增 revision。若提交的 revision 已过期，接口返回 `409 context_conflict` 和最新上下文；发起页显示当前选择与最新值，并允许“采用最新上下文”或“继续使用此页选择”。
5. 网络或持久化失败显示明确状态和重试入口，不将写入悄悄落到 `localStorage`。
6. 兼容接口 `/api/director/context` 调用相同校验、持久化和广播流程，不再直接写运行态。

`preview` 和 `onAir` 仍遵循现有“编辑后推送”的区别；`live.context`、倒计时等现场状态仍即时广播，不混入场景推送流程。

## 7. 工作流与导航

概览页新增“建议下一步”区，建议由数据完整度和当前上下文计算，不根据时钟自动切换阶段，也不强迫用户遵循：

- **赛前准备**：补队伍名单 → 完成分组 / 对阵 → 制作宣传图。
- **赛中执行**：打开当前场次对局 → 核对双方与局次 → 导播预览 / 推送。
- **赛后整理**：核对对局数据 → 回填赛果 → 导出图表。

每项操作直接跳到对应 `?view=` / `?tab=`，跨页链接携带稳定 ID，而非只靠队名或标签文本。侧栏入口始终可用。顶部上下文条展示当前权威上下文及其来源状态；状态不完整时提供“去对局数据选择”入口。

## 8. 分阶段实施

### 阶段 0：契约盘点与迁移预览

- 清点所有队伍和上下文读写路径、旧数据形状、旧页面引用。
- 为 `teams.json` 对照 `library.json` 生成只读差异报告。
- 更新项目地图，记录权威数据、页面职责和数据流。
- 不写现有赛事数据，不删除旧文件。

### 阶段 1：统一队伍数据服务

- 建立队伍仓储 / 领域服务，以 `library.json` 为唯一写入来源。
- 让 `/api/director/teams` 成为兼容适配器；迁移导播台名单编辑和相关页面到 canonical team API。
- 提供 dry-run 和显式确认的 `teams.json` 导入流程，保留原文件及备份。
- 移除“合并两套队伍”的隐式读取行为。

### 阶段 2：统一上下文与状态广播

- 建立上下文服务和持久化 revision。
- 将生成器、工作台顶栏、导播台和 OBS 迁移到同一上下文协议。
- 增加过期 revision 冲突提示、服务不可用提示和重试行为。
- 保留 `live.context` 作为 SSE 快照字段，所有旧接口代理到新服务。

### 阶段 3：工作流导航

- 概览页加入赛前 / 赛中 / 赛后建议步骤和数据就绪提示。
- 关键跨页入口通过 ID 跳转并保留上下文。
- 侧栏保留所有直接入口；不自动改动当前场次或推送直播画面。

### 阶段 4：清理重复实现

- 搜索并验证 `director/director.html`、构建脚本和本地存储回退没有被运行入口或用户工作流依赖。
- 对还需兼容的功能先标注弃用并留一段过渡期；确认迁移后再单独提交删除。
- 本阶段不删除用户数据，也不自动删除旧队伍文件。

各阶段独立验收；阶段 1 不依赖阶段 2，阶段 3 使用阶段 2 的上下文协议。每一阶段完成后更新项目地图和使用说明。

## 9. 兼容性与安全边界

- 保持 `/`、`/director`、`/generator` 和 `/obs/*` 地址不变。
- 保持现有赛事 JSON 结构；只允许上下文增加 `revision` 等可选元数据。
- 不更改 OBS 场景尺寸、推送 / 丢弃语义或透明输出行为。
- 不引入 SQLite、前端框架、外部服务或运行时依赖。
- 不自动覆盖队伍冲突、不自动合并不同系列赛的队伍、不启动时修改用户文件。
- 服务器不可用时明确阻止写操作并提示；任何未来 localStorage 导入必须由用户主动触发并先预览差异。

## 10. 验收标准

- 队伍通过任一兼容入口修改后，`library.json` 是唯一变更来源，赛程、宣传图、导播台和 OBS 读到相同 ID、队名和名单。
- 迁移 dry-run 能识别精确匹配、疑似同名和未匹配队伍；未确认时不写数据；确认导入后可重复运行且不重复建队。
- 上下文切换后，`context.json`、导播 `live.context`、顶栏和 OBS 一致；重启后仍能恢复。
- 旧 revision 更新会返回冲突并呈现清楚的恢复选择；存储失败时不会广播未保存的上下文。
- 多标签页刷新不会自动把陈旧上下文写回；用户显式选择后仍能切换当前场次。
- 概览页的赛前、赛中、赛后入口都能跳到对应视图并保留当前 series / match / game。
- 旧 URL 和未迁移的页面兼容接口仍可工作；所有迁移均保留备份且不删除赛事数据。
- 对每一阶段执行针对数据仓储、兼容接口、冲突处理、页面跳转与 OBS 消费的回归验证；测试不得写入真实赛事数据。

## 11. 风险与应对

- **旧队伍资料互相冲突**：先报告并由用户选择，不以姓名相同推断可覆盖。
- **旧接口仍有隐式依赖**：保留适配器，通过代码引用和运行回归确认后再退役。
- **同步写入多个 JSON 资源失败**：本设计范围内的写操作每次只更新一个 canonical JSON 资源；跨资源事务不在本轮范围内，未来若需要必须先设计恢复协议。
- **多标签冲突提示过多**：revision 只针对显式上下文变更；页面初始读取不写入，服务端 SSE 更新本地 revision。
- **旧 localStorage 存有唯一数据**：不自动覆盖服务端；提供独立导入预览，并把冲突列清楚。

## 12. 非目标

- 不重画赛程、宣传图、对局数据或 OBS 场景。
- 不改英雄胜率统计口径、抓取流程、OCR 或 AI 服务。
- 不做多人协作、云同步、远程访问或账号权限。
- 不在本轮设计批准后直接批量迁移赛事文件；迁移必须经过独立 dry-run 和确认流程。
