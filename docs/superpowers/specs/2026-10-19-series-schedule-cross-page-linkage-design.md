# 系列赛赛程跨页面联动 · 设计说明

日期：2026-10-19
适用项目：`D:\Agent data\Codex\PKC比赛图表制作`

## 1. 问题陈述

当前系统里，赛程图、队伍库、对局数据各自保存了一部分“同一件事”，但没有任何一方是唯一权威：

- **队伍身份有三套入口**：`② 队伍库` 可以新建、改名、改名单；`① 对局数据` 的队名输入框在失焦时也会改名或新建队伍；`⑤ 赛程图` 又从队伍库下拉选队。操作者在一处改了名字，另一处看到的结果取决于是否刷新、是否同名匹配。
- **“淘汰”有两个来源**：`② 队伍库` 有手动“标记淘汰”，`⑤ 赛程图` 又根据胜负自动把队伍送进败者组/淘汰。两边可能互相矛盾。
- **分组存了两份**：`⑤ 赛程图` 的 `groups` 是抽签结果，队伍对象上的 `group` 是导入名单时的旧值。改了抽签，队伍库里的分组标签不会跟着变。
- **对局与赛程没有连接**：`① 对局数据` 只有“第1局、第2局……”的扁平列表，一局数据不知道自己属于 16 强第 5 场还是胜者组半决赛 1。录完数据后，还要回到 `⑤` 手动再填一遍大比分和晋级。
- **导播台不知道“现在是哪一场”**：赛间板、BP、数据图各自从队伍列表或生成器 iframe 里临时取值。切了场次以后，导播台可能还在用上一场的队名或上一局的数据图。

因此，本次改造的核心不是再加几个按钮，而是先确定**数据主权**，再让所有页面围绕同一个“当前场次 + 当前局”联动。

## 2. 目标与非目标

### 目标

1. 每一份数据只有一个可写入口，其它页面只读或只做选择。
2. `⑤ 赛程图` 的每一场对阵可以直接打开 `① 对局数据` 的对应场次。
3. `①` 录完的局分可以一键回填 `⑤` 的大比分和晋级结果，但必须由操作者明确点击。
4. 导播台、BP、赛间板、赛程图、赛后数据图共享同一个“当前系列赛 / 场次 / 局”上下文。
5. 页面刷新、切换标签、OBS 重连后，仍然回到正确的场次和局。
6. 旧数据（没有场次标记的局）完整保留，归入“未关联赛程”，不丢失、不改写。

### 非目标

- 不自动替操作者抽签，也不自动推进淘汰赛对阵。
- 不改变现有的 OCR / DeepSeek 识别流程和数据结构。
- 不引入数据库、框架或新的运行时依赖。
- 不清理 `数据/library.json`、`数据/bracket.json`、`数据/matches.json` 中的现有内容。
- 不把赛程图重画成另一种版式；本次只加联动所需的最小视觉标识。

## 3. 数据主权

| 数据 | 唯一来源 | 可写页面 | 只读消费方 |
| --- | --- | --- | --- |
| 队伍 ID、队名、主色、选手名单 | `数据/library.json` 的 `series[].teams[]` | `② 队伍库` | `①`、`⑤`、导播台、OBS |
| 分组（A/B/C/D 第 N 名） | `数据/bracket.json` 的 `groups` | `⑤ 赛程图` | `②`（只读标签）、`⑤` 下拉标签 |
| 对阵、轮次、晋级、大比分 | `数据/bracket.json` 的 `draw` / `win` / `score` | `⑤ 赛程图` | `①`、导播台、OBS |
| 单局战绩（KDA、经济、伤害等） | `数据/matches.json` 的 `games[]` | `① 对局数据` | `⑤`（只读统计）、导播台、OBS |
| 当前系列赛 / 场次 / 局 | `数据/context.json` + 导播台 `live.context` | `① 对局数据` | 导播台、OBS |

补充规则：

- 队伍对象上的 `group` 字段降级为“导入时的初始提示”，显示时优先用 `bracket.groups` 推导；`⑤` 改分组后同步回 `t.group`，只作为缓存，不再作为第二权威。
- 队伍对象上的 `eliminated` 字段保留，但语义改为“手动停用 / 不参与抽签”。真正的“已淘汰”由 `bracket.win` 推导，显示为只读状态。
- 一局数据的 `matchKey` 为空字符串时，表示“未关联赛程”，用于兼容历史数据。

## 4. 用户流程

### 4.0 推荐工作流（赛前 → 赛中 → 赛后）

1. **赛前**：`② 队伍库` 建队、录名单；`⑤ 赛程图` 填分组和抽签。
2. **赛中**：`⑤` 点该场 `📊` → `①` 录本局 → `⑤` 点 `回填` 更新大比分 → 下一局。
3. **直播**：`①` 选好当前局；导播台自动跟随；赛间/BP/数据图照常推送。
4. **赛后**：`①` 只导出当前局；`④` 的“本场所有局”只对比这一场，不跨场拼接。

### 4.1 从赛程图开始录一局

1. 打开 `⑤ 淘汰赛赛程图`，找到 `16强5 等我刷把电刀 vs 别让我取名`。
2. 点这一行右侧的 `📊` 按钮。
3. 如果这场还没有数据：系统新建一局，`matchKey = "R16-5"`，蓝方/红方自动带入赛程里的两支队伍，标签为“第1局”，并切到 `① 对局数据`。
4. 如果这场已有数据：系统切到 `①` 并选中这场最近的一局。
5. 在 `①` 里正常 OCR / 手填；顶部始终显示“16强5 · 等我刷把电刀 vs 别让我取名 · 第1局”。

### 4.2 从对局数据切场次

1. `①` 顶部新增“赛程场次”下拉，按轮次分组列出所有已确定对阵的场次。
2. 选中一个场次后，下面的局按钮只显示这个场次的局；`＋ 本场新一局` 新建的局自动带上该场次。
3. 选择“未关联赛程”时，显示历史遗留的扁平局，行为和现在一致。

### 4.3 回填赛果

1. `⑤` 的每场对阵显示“已录 N 局 · 2:1”。
2. 点 `回填`，系统弹出确认：“用这场已录的 3 局把比分填成 2:1，并把 XXX 标记为晋级？”
3. 确认后只写 `score` 与 `win`，不动 `draw`、不动局数据。
4. 如果局分相同，只填比分，不标记晋级。

### 4.4 导播台跟随

1. `①` 每次切换系列赛、场次、局，或改完队名后，向 `/api/director/context` 发布当前上下文；
   页面加载完成时也发布一次，保证刷新后导播台和 OBS 能回到正确的场次。
2. 导播台顶部显示“16强5 · 第2局”的上下文条。
3. 赛间板默认勾选“跟随当前场次”，自动把蓝/红队名填成当前场次的两队；操作者仍可手动改，改完照常推送。
4. `开始 BP` 的队名优先级改为：当前上下文 → 赛间板设置 → 队伍库前两支。
5. `推送本局六张` 的每一张都带上 `matchKey`、`matchLabel`、`gameLabel`；OBS 数据图角标显示“16强5 · 第2局 · 3 / 6”。
6. OBS 赛程图把当前场次加金色高亮；BP / 阵容 / 赛间板显示当前场次条。

## 5. 数据模型

### 5.1 局对象新增字段

```js
{
  id: "abc1234",
  label: "第2局",
  matchKey: "R16-5",   // 新增；"" = 未关联赛程
  ourId: "team_a",
  oppId: "team_b",
  ourScore: "12",
  oppScore: "8",
  result: "win",
  // ...其余字段不变
}
```

`matchKey` 直接使用 `bkTree()` 已有的稳定键：`R16-1` … `R16-8`、`WB1-1` … `WB1-4`、`WB2-1`、`WB2-2`、`WBF`、`LB1-1`、`LB1-2`、`LB2-1`、`LB2-2`、`LB3`、`LBF`、`GF`、`GF2`。

不新建 `schedule.json`。赛程的场次实体已经由 `bracket.draw` + `bkTree()` 唯一确定，再存一份会制造第二个权威。

### 5.2 上下文对象

保存到 `数据/context.json`，同时通过导播台 SSE 广播：

```js
{
  seriesId: "nb24ulp",
  seriesName: "2026 薄扶林王者杯",
  matchKey: "R16-5",
  matchLabel: "16强5 · 等我刷把电刀 vs 别让我取名",
  matchRound: "16强赛",
  gameId: "kp1vmgc",
  gameLabel: "第1局",
  blueId: "1364zpb",
  redId: "ztg0fas",
  blueTeam: "等我刷把电刀",
  redTeam: "别让我取名",
  updatedAt: "2026-10-19T02:00:00.000Z"
}
```

`context.json` 只存“指针”，不存战绩。页面刷新后由 `①` 重新发布；服务启动时先读它兜底，避免 OBS 先于导播台打开时没有上下文。

### 5.3 赛程高亮不复制场次指针

赛程快照继续只存分组、对阵、胜负和比分。OBS 渲染赛程图时，从同一份 `live.context.matchKey`
取当前场次并加高亮，不再往 `bracket` 快照里塞一份 `activeMatchKey`。

这样只有 `context` 一个“当前场次”指针，避免抽签快照和上下文各说各话。

## 6. 跨页协议

### 6.1 生成器 → 服务端

- `POST /api/store/context`：持久化当前上下文。
- `POST /api/director/context`：立即更新导播台 `live.context` 并触发 SSE `live` 事件。
- `POST /api/director/bracket`：现有接口，快照内容不变；OBS 另从 `live.context.matchKey` 取高亮场次。

### 6.2 服务端 → 导播台 / OBS

- SSE `live` 事件的 `state.live.context` 携带上下文。
- `GET /api/director/state` 首次加载时也返回 `live.context`。
- OBS 不额外请求接口，只消费 SSE。

### 6.3 生成器内部

- `publishContext(delay)`：防抖发布上下文，默认 0 ms；同时直接保存 `数据/context.json`，
  `saveAll()` 里再兜底保存一次。这样只刷新页面、不改数据也会落盘。
- `S.game.matchKey` 是唯一读取入口；不再维护 `S.series.currentMatch` 这类第二状态。

## 7. 冲突与失败处理

| 情况 | 处理 |
| --- | --- |
| 已关联的局，队伍与赛程对阵不一致 | `①` 顶部黄色提示“赛程是 A vs B，这局录的是 C vs D”；不自动改任何一边 |
| 抽签改动导致已关联局的队伍失效 | `⑤` 顶部红色提示列出受影响场次；不自动删除局数据 |
| `matchKey` 指向已不存在的场次 | 归入“失效关联”，在 `⑤` 提示；`①` 仍可通过“未关联赛程”找到该局 |
| 删除队伍 | 现有逻辑清空局的 `ourId/oppId`；`⑤` 显示“队伍已删除”，不自动改对阵 |
| 局分为平局 | `回填` 只写比分，不写 `win`，并提示“平局不标记晋级” |
| 导播台未收到上下文 | 顶部显示“未选择场次”；赛间板/BP 回退到现有手动选择逻辑 |
| `context.json` 损坏 | 服务端忽略并保持 `live.context = null`，页面正常启动 |
| 两个生成器标签同时打开 | 后写入的上下文生效；这是本地单操作员场景，明确接受 |

## 8. 页面职责

### `① 对局数据`

- 顶部新增“赛程场次”下拉和“本场新一局”。
- 局按钮按场次过滤。
- 队伍字段改为“从队伍库选择”，不再隐式建队或改名。
- 绑定场次后，蓝/红方下拉只保留该场次的两支队伍；新建小局自动与上一局互换红蓝方。
- “本局信息”卡头提供醒目的“⇄ 交换红蓝方”按钮。
- 队名旁提供“去队伍库编辑”入口。
- 显示当前场次面包屑和队伍不一致提示。

### `② 队伍库`

- 仍是队伍身份和名单的唯一编辑处。
- 分组和“已淘汰”改为只读显示，来源是 `⑤`。
- 手动按钮改名为“停用 / 启用”，语义是“不参与抽签”。
- 队伍卡片增加“赛程”入口，切到 `⑤` 并滚动/高亮该队下一场未决比赛。

### `④ 多局与导出`

- “导出包含所有局”改为“导出包含本场所有局”。
- 多局对比、逐张下载、ZIP 打包都只取当前 `matchKey` 的局；历史局在“未关联赛程”下单独成组。
- 这样不会把 16 强第 5 场和胜者组半决赛的局拼进同一张多局对比图。

### `⑤ 淘汰赛赛程图`

- 每场对阵增加 `📊`（录数据）和 `回填`（用局分写大比分）。
- 显示“已录 N 局 · a:b”。
- 分组表仍是分组唯一写入口；改动后同步 `t.group` 缓存。
- 新增关联冲突提示区。

### 导播台

- 顶部上下文条。
- 赛间板“跟随当前场次”开关。
- BP 队名优先取上下文。
- 数据图状态显示当前场次和局。

### OBS

- 赛程图当前场次金色高亮。
- BP / 阵容 / 赛间板显示上下文条。
- 数据图角标显示场次和局。

## 10. 需要用户确认的决策

以下三项已按推荐方案写进计划，若用户不同意，执行前需要改计划：

1. **`①` 的队名输入改为只读下拉**，改名/新建统一去 `②`。这是消除“三个入口”的关键；代价是临时纠正 OCR 队名要多一步。
2. **`回填` 是显式按钮，不自动推进对阵**。避免改一局数据就悄悄改变赛程图。
3. **导播台默认跟随 `①` 的当前场次，但保留手动覆盖**。适合单操作员现场，也不剥夺临场改队名的能力。
